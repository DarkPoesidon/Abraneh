# معماری به‌روزرسانی ۱.۳

این سند برای نگهدارنده است؛ کاربر نهایی [راهنمای به‌روزرسانی](AUTO-UPDATE.fa.md) را بخواند.

## مرز اعتماد و راه‌اندازی

نصب‌کننده با رضایت صریح، Worker خصوصی `name-updates` و Durable Object مبتنی بر SQLite می‌سازد. `workers.dev` و preview آن خاموش‌اند. Worker پیام‌رسان فقط با Service Binding و Secret مشترک به آن دسترسی دارد. API عمومی پیام‌رسان نیز نشست معتبر و مدیر اصلیِ ثبت‌شده در slot 1 را لازم دارد. توکن کلادفلر فقط در Secret به‌روزرسان است؛ به Worker عمومی، GitHub یا دادهٔ خروجی وضعیت فرستاده نمی‌شود. اعتبار توکن محدود به مجوزهای واقعی حساب است؛ API Token نصب دسترسی Workers/D1 حساب انتخاب‌شده دارد و مجوز محدود به یک Worker نیست.

از نصب قبلی، DB و namespace گفتگوها و Secretهای موجود به ارث می‌رسند؛ `TELEGRAM_KEY` برای رمزکردن توکن ربات افزوده می‌شود. نصب بدون انتخاب به‌روزرسان، CF_TOKEN را فقط در حافظهٔ نصب‌کننده دارد. به‌روزرسان موجود هنگام نصب دوباره بی‌صدا غیرفعال نمی‌شود. تمدید توکن از API مدیر، فقط Secret به‌روزرسان خصوصی را تغییر می‌دهد و کلیدهای پیام‌رسان را عوض نمی‌کند.

## پروتکل انتشار و امضا

1. نسخهٔ package، برنامه، meta رابط، کش SW و تگ `installer-vX.Y.Z` باید یکسان باشند.
2. CI لینوکس، macOS و ویندوز تست‌ها و نصب‌کننده را بررسی می‌کند. لینوکس JSON فایل‌های payload را با مسیر نسبی و base64 می‌سازد؛ sourceCommit و minimumUpdaterVersion نیز داخل آن است.
3. فقط گردش‌کار تگ، Secret مخزن **WIHM_UPDATE_SIGNING_KEY** را برای امضای Ed25519 به اسکریپت می‌دهد. کلید خصوصی نباید وارد سورس یا خروجی لاگ شود. کلید عمومی متناظر در `src/update-key.ts` پین شده است.
4. تگ بدون کلید یا با کلید نامنطبق شکست می‌خورد. ساخت توسعه می‌تواند بدون امضا باشد، ولی به‌روزرسان چنین بسته‌ای را نمی‌پذیرد.
5. انتشار مشترک شامل ZIP و tar.gz نصب‌کننده، `wihm-update.json`، `wihm-update.sig`، APK یونیورسال، فایل نصب ویندوز و `SHA256SUMS` برای همهٔ این فایل‌هاست. اسکریپت `check-update-bundle.mjs` امضا، ساختار و برابری فایل‌ها با payload واقعی را بررسی می‌کند.
6. دریافت فقط از مسیر ریلیز مخزن ثابت انجام می‌شود. امضا روی بایت‌های خام JSON، پیش از parse بررسی می‌شود؛ تعداد/حجم/مسیر فایل‌ها، base64، فایل‌های اجباری و نوع Static Assets محدودند. توکن کلادفلر در این درخواست‌ها وجود ندارد.

چرخاندن کلید خصوصی بدون برنامه باعث قطع اعتماد نصب‌های قبلی می‌شود. کلید عمومی را بی‌هماهنگی تغییر ندهید؛ نسخهٔ واسطِ مورد اعتماد یا ارتقای یک‌باره با نصب‌کننده لازم است. حذف/انقضای توکن انتشار را قطع می‌کند ولی سرویس موجود را خاموش نمی‌کند.

## اجرای پایدار و حفظ اطلاعات

DO مراحل prepare، database، publish، verify و updater را با alarm و وضعیت پایدار ادامه می‌دهد. نسخه و digest تأییدشده در کار ثابت می‌مانند. مهاجرت‌ها ثبت‌شده و قابل تکرارند؛ پاسخ گم‌شده نباید باعث چرخاندن Secret یا اجرای دوبارهٔ مهاجرت اولیهٔ DO شود. پذیرش انتشار با پاسخ گم‌شده، از نسخهٔ واقعی تنظیمات تشخیص داده می‌شود. پس از بررسی سلامت نسخهٔ مقصد، به‌روزرسان نیز از همان بسته ارتقا می‌یابد. downgrade خودکار رد می‌شود. خطاها با تأخیر و سقف تلاش محدود تکرار می‌شوند؛ وضعیت شکست برای مدیر قابل مشاهده است.

این طرح پشتیبان‌گیری، تراکنش اتمیک بین انتشار Worker و D1 یا rollback خودکار نیست. مهاجرت‌های بعدی باید با نسخهٔ فعلی سازگار باشند و بازیابیِ مستقل خود را داشته باشند. سهمیه و انقضای توکن، دسترسی شبکه و حذف دستی منابع همچنان محدودیت عملیاتی‌اند.

Cron پیام‌رسان هر ۱۵ دقیقه بیدار می‌شود؛ TTL بررسی ریلیز چندساعته است. اعلان نسخهٔ سرور فقط به نشست‌های معتبر مدیر با اعلان فعال فرستاده می‌شود؛ fan-out صفحه‌بندی و cursor پایدار دارد. مجوز اعلان به‌معنی مجوز انتشار نیست.

## رضایت در دستگاه

Service Worker سیاست نسخهٔ فعال، نسخهٔ تأییدشده و روش دریافت را در IndexedDB مشترک نگه می‌دارد. نصبِ کش نسخهٔ تازه در حالت تأیید بدون رضایت رد می‌شود؛ به همین دلیل بستن همهٔ تب‌ها «فعلاً نه» را دور نمی‌زند. نسخهٔ meta داخل HTML دریافت‌شده باید با کش جدید یکسان باشد؛ کش ناقص حذف می‌شود. API از شبکه خوانده می‌شود و فایل‌های shell تأییدشده cache-first هستند. خودکار تا خالی‌شدن composer و outbox صبر می‌کند؛ تغییر controller هم وضعیت نوشتن را دوباره بررسی می‌کند.

## آزمون و محدودیت شواهد

تست‌ها امضای مخدوش/ناشناخته، مسیر نامعتبر، مجوز مدیر، تمدید دسترسی، قطع پس از پذیرش انتشار برنامه و خودبه‌روزرسان، و ادامه پس از ساخت مجدد runtime با ذخیره‌سازی پایدار را پوشش می‌دهند. Chrome واقعی رد دریافت پس از بسته‌شدن همهٔ تب‌ها، تأیید، حالت دستی و انتظار برای پایان نوشتن را آزمایش می‌کند. تست اعلان payload رمز‌شده را مستقل رمزگشایی می‌کند. این شواهد، جای استقرار روی حساب واقعی کلادفلر یا تحویل اعلان روی گوشی واقعی را نمی‌گیرند.
