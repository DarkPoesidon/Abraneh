# WIHM Installer

A Persian local-browser installer. Runtime dependency: Node.js 22+. No npm install, Wrangler, workerd, native extensions or Git on the end user's device. `install.ps1` and `install.sh` prepare Node if needed; Termux uses its own `nodejs-lts` package instead of a desktop Linux binary.

Build from the repository root:

```sh
npm ci
npm run installer:build
node scripts/check-installer-assets.mjs
node scripts/check-installer.mjs
npm run installer:start
```

The distributable is `dist/WIHM-Installer`. CI builds ZIP and tar.gz archives and SHA-256 checksums. A tag named `installer-v*` publishes them after Windows, macOS and Linux checks pass. Package and tag versions must agree. Build metadata, the installer footer and release title derive from the package version. Keep `src/version.ts`, the messenger version label and its Service Worker cache version aligned; include `docs/releases/<version>.fa.md`. Bootstrap launchers download the latest stable package, while an already-extracted old package remains that old version.

`cloudflare.mjs` uses the fixed official API origin and never displays raw provider error text. `deploy.mjs` checks ownership, prepares a workers.dev address, creates or reuses D1, initializes the additive schema, applies versioned SQL migrations, uploads Static Assets, uploads the precompiled Worker with its initial SQLite Durable Object migration, and enables the public address. Updating an installer-managed Worker inherits `JWT_SECRET` using strict binding inheritance; it does not regenerate the secret or replay the initial Durable Object migration. SQL migrations are recorded in `schema_migrations` and must be replay-safe if a response is lost. Unrecognized Workers or databases are refused. The 1.0 ownership marker is accepted for upgrading; the new marker deliberately makes 1.0 installers refuse an upgraded Worker, preventing accidental downgrade. Manually installed instances need a future explicit migration path.

`server.mjs` binds only to `127.0.0.1` on a random port. A random session key in the initial URL fragment authorizes API requests; it is removed from the visible URL and retained in tab session storage. Host, Origin and fetch-site checks restrict browser access. API credentials stay in the server process's memory. Stopping the installer drops credentials. The on-disk recovery journal contains only database identifiers, scoped by account ID and Worker name. No cloud resources are automatically deleted after a partial failure.

Recovery is conservative. If a database-create response is lost before its ID can be journaled or its ownership table written, an empty same-name database may be left behind; it is refused rather than adopted by guessing. Choose another name or inspect the resource in Cloudflare. Automatic database deletion and rollback are intentionally absent.

The `/api/health` endpoint checks JWT configuration and required D1 tables and reports the application version. Installation verifies that the returned version matches the target. A failed public connectivity check after an accepted Cloudflare deployment produces a distinct pending result, not a success claim. This is a readiness check; it does not prove WebSocket connectivity on every carrier or network. See `docs/UPDATE.fa.md` for the distinct server-upgrade and browser-shell update steps.

Verification covers deployment requests with a simulated Cloudflare API, multipart assets, first deployment, interrupted installation, retry after an accepted upload with a lost response, stable database/secret reuse, conflicting resources, downgrade refusal, migration replay, local-browser isolation and the packaged launcher. A persistent Miniflare upgrade test starts with the 1.0 D1/room layouts and a legacy JWT. Messenger integration tests also cover deduplication, a failed D1 indexing batch, receipts, unread counts, revoked sessions, flooding limits and oversized input. Real Chrome QA covers offline reload and delivery between two users, device revocation, finding the first unread across history pages and mobile widths. The owner reported successful Windows installation/deployment of 1.0. The 1.1/1.2 live-account upgrades, real-device push delivery and a physical Android/Termux run still need field verification; CI alone does not establish them.

Version 1.2 bundles `@block65/webcrypto-web-push` 2.0.0 into the Worker; the installer itself still requires only Node built-ins. It creates a VAPID P-256 pair on the first compatible deployment and strictly inherits both existing push keys on updates. A fresh `ADMIN_SETUP_TOKEN` is set for each deployment and returned only to the authenticated local wizard, never the installation journal or saved receipt. The claim route never replaces an already assigned administrator. An owner who loses an unclaimed code may rerun the same installation to obtain a usable new one.

Migration 0002 adds daily-use tables without changing the original layouts. Existing group ownership uses the creator-first membership insertion order of shipped 1.0/1.1, including tied timestamps. Message mutations remain canonical in room SQLite; revisions guard indexing and late client snapshots. Password versions reject old or racing sessions. Search/changes/bookmarks overlay canonical room data; personal hides apply before history pagination. Roles and block status are checked on frames and broadcasts. Group membership authorization is batched per room. The service-admin controls here cover registration and reports; the fuller service-management work remains Priority 3. See `docs/DAILY-USE.fa.md` and `THIRD-PARTY-NOTICES.md`.

Resource checks use bounded push fan-out (24 subscriptions per room alarm page), persisted cursors, batched authorization and JSON membership arrays rather than one database call per online member. Saved messages use cursor pages of eight; quoted parents are fetched in a batch. Literal `instr` search avoids D1's LIKE-pattern length limit for Persian UTF-8 input. See the primary [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) and [Workers subrequest update](https://developers.cloudflare.com/changelog/post/2026-02-11-subrequests-limit/). Daily account quotas and device/network delivery still require operational monitoring; these local checks do not establish production capacity.

The 1.2.1 UI patch uses an unmodified local Vazir variable WOFF2 (v30.1.0), bundled license/attribution and an offline font cache. The loopback installer serves the same font through an explicit static route with `font-src 'self'`; the Worker asset uploader labels WOFF2 as `font/woff2`. `tests/browser/navigation.mjs` verifies the font bytes, actual Persian weight loading, offline Service Worker font delivery and responsive navigation; `tests/browser/daily-use.mjs` checks the existing messaging flows through the new menus. Telegram reference observations and REA Evidence IDs are in `docs/design-notes/navigation-1.2.1.fa.md`.

Version 1.2.2 fixes the flat-only asset traversal that rejected the font directory before any upload in 1.2.1. The uploader now walks nested directories, uses slash-separated manifest URLs on every OS, deduplicates content by hash and still rejects links and unsupported files. Deployment tests copy the real public tree, including the font, and cover restarting after an interrupted asset upload without creating another database. `scripts/check-installer-assets.mjs [installer-directory]` invokes the built or downloaded package's uploader with its actual payload against a simulated API; it verifies every manifest path/hash/size, exact multipart bytes, font MIME, multiple buckets and a fully cached retry. It runs in the three-platform CI before packaging. `scripts/check-installer.mjs [installer-directory]` also checks English-only terminal output while the browser UI remains Persian. These checks do not establish deployment success on a real Cloudflare account.

Version 1.2.3 performs a full Termux APT upgrade before installing dependencies, keeping existing configuration files. This is required because Termux does not support partial upgrades: the old guide reproduced a curl/OpenSSL linker failure on fresh official Termux 0.118.3 under Android 16. Direct `apt-get` also avoids `pkg`'s curl-based mirror checks when recovering that failure. The guide upgrades before its first curl invocation as well. `tests/termux-bootstrap.test.mjs` executes the real shell launcher on Linux/macOS with simulated package commands to verify upgrade order, missing/existing Node, PREFIX-only detection, and absence of desktop runtime downloads. These simulated tests are separate from Android runtime verification. See the primary [Termux environment documentation](https://github.com/termux/termux-packages/wiki/Termux-execution-environment).

Android Chrome sends `Sec-Fetch-Site: cross-site` with `navigate`/`document` when opened from Termux. The local server permits this only for `GET /`, the public entry document. Foreign Origin/Host, cross-site fetches, frames and every cross-site API request remain rejected; session authorization and POST origin checks are unchanged. The installer regression test exercises the observed Android headers and each refusal case.
